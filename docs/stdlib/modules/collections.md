## Overview

> **Overview vs Reference:** This section is curated prose — it explains when and how to use this module family. The sections below are exhaustive generated reference tables sourced directly from `std/manifest.toml` and source doc comments.

The `std::collections` family provides the primary collection data structures for Arukellt programs: hash maps, double-ended queues, FIFO queues, LIFO stacks, linked lists, min-heap priority queues, sorted maps, and bitsets. The canonical HashMap and linear-collection surfaces are generic and statically monomorphized; lower-level containers remain available for compatibility and compiler-facing work.

**Recommended API highlights:**

| API | Purpose |

| `.contains_key` / `.remove` / `.len` | Typed lookup, removal, and size operations. |
| `HashSet::new` / `.insert` / `.contains` | Unordered `i32` / `String` set with membership, aggregate, and ADR-086 trait methods. |

## Module `std::collections::hash`

- Source: [`../../../std/collections/hash.ark`](../../../std/collections/hash.ark)
- Manifest-backed functions: 0
- Stability: n/a

Hash-based collection helpers.

Provides the raw HashMap and HashSet implementation layer backed by a flat
`Vec<i32>` with open addressing and linear probing. The canonical source
surface is `HashMap::new<K,V>()` and receiver methods; the compiler
monomorphizes those calls to per-pair implementation functions and uses
these helpers where the selected representation is linear memory.

### Generic dispatch

`impl HashMap<K,V>` in `std::collections::hash_map` is the only public
spelling: `HashMap::new<K,V>()` plus receiver methods. The `i32`->`i32`
pair lowers directly to the flat store functions in this module
(`hashmap_new`, `hashmap_insert`, `hashmap_get_option`,
`hashmap_contains`, `hashmap_remove`, `hashmap_size`, `hashmap_keys`,
`hashmap_values`, `hashmap_entry_pairs`); the other supported pairs lower
to the non-public functions in `std::collections::hash_string` / `hash_fn`
/ `hash_str_fn`. No `HashMap_*` free builtins remain.

### Compatibility implementation

The functions in this module operate on `Vec<i32>` and serve as the raw
implementation layer for the `i32`->`i32` family.

Every function in this module is a non-public MIR lowering target. The
`hashset_*` store functions serve `HashSet<i32>`;
`std::collections::hash_string` owns the equivalent `HashSet<String>`
targets. The `hashmap_*` functions serve `HashMap<i32, i32>`, including
the capacity / bulk-maintenance group (`capacity`, `with_capacity`,
`reserve`, `try_reserve`, `shrink_to_fit`, `clear`, `drain_pairs`,
`remove_entry_pair`, `extend`) and `hashmap_entry_pairs`. Their public
free spellings were retired by #917 after the method surface landed.

### Hash policy

All hash functions in this module use a consistent FNV-1 algorithm
(offset_basis=216613626, prime=16777619) applied byte-by-byte over the key
representation.  This matches the canonical hash policy in
`std::core::hash` and avoids policy drift between i32-keyed and
String-keyed hash map operations.

### Layout

`Vec<i32>` backing store:
`[capacity, size, ...keys(cap), ...values(cap), ...flags(cap)]`,
where flags are `0 = empty`, `1 = occupied`.

## Module `std::collections::deque`

- Source: [`../../../std/collections/deque.ark`](../../../std/collections/deque.ark)
- Manifest-backed functions: 0
- Stability: n/a

`Deque<T>`, `Queue<T>`, and `Stack<T>` — linear collections over shared
two-stack storage.

Storage is a pair of `Vec<T>` stacks: `front_items` holds the front half in
reverse order and `back_items` holds the back half in order. When one side
empties during a pop, the other side is reversed into it, so every element
moves at most once per traversal between the two stacks. A growable ring
buffer would need preallocated element slots; a generic struct field of
`Vec<Option<T>>` (or raw slot writes) does not lower on `wasm32-gc`, so this
representation is used instead while keeping the same public contract.

`capacity` / `reserve` expose the logical reservation: pushes grow it and
`reserve` rebuilds both stacks through `Vec::with_capacity` so the
reservation is backed by the vector allocators.

`Queue<T>` and `Stack<T>` are restricted newtypes over `Deque<T>`. Their
`push` / `pop` names encode the direction so callers do not have to
remember which `Deque` end implements FIFO or LIFO. They share the
`DequeIter` / `DequeIntoIter` cursors instead of declaring look-alike
iterator types.

Cursors hold the collection handle rather than a borrowed reference, so the
type checker does not yet reject a push / pop / clear while an iterator is
alive. Do not structurally modify a collection during iteration; the
borrow / lifetime design will enforce this later (ADR-086 §5).

`FromIterator<VecIter<T>>` fills the logical front-to-back order from a
`Vec` cursor and `Eq` compares length plus that order while ignoring the
capacity reservation. ADR-078 §3 allows one parametric impl per
(trait, self constructor), so the collection's own cursors cannot be added
as further `FromIterator` sources; the shared `VecIter<T>` source is used
for `Deque`, `Queue`, and `Stack`.

**Availability:** All targets (`wasm32` + `wasm32-gc`). No host capability required.

`LinkedList<T>` and legacy free-function helpers for a doubly-linked list.

`LinkedList<T>` is a `Vec`-backed node pool with a free list. Node metadata
(`prev` / `next` indices and a value index) lives in parallel `Vec<i32>`
vectors, and element values live in an append-only `Vec<T>` log. Both-end
push / pop and peek are O(1); front-to-back traversal is O(n). `clear` drops
the value log and keeps the node-pool capacity.

The older `linked_list_*` free functions below operate on a monomorphic
`Vec<i32>` layout and remain only for the ADR-086 migration window. New code
should use `LinkedList<T>`.

Cursors hold the list handle rather than a borrowed reference, so the type
checker does not yet reject a push / pop / clear while an iterator is alive.
Do not structurally modify a list during iteration; the borrow / lifetime
design will enforce this later (ADR-086 §5).

`FromIterator<VecIter<T>>` appends the cursor values front to back, and `Eq`
compares length plus iteration order while ignoring node-pool state.
ADR-078 §3 allows one parametric impl per (trait, self constructor), so the
list cursors cannot be added as further `FromIterator` sources.

**Availability:** All targets (`wasm32` + `wasm32-gc`). No host capability required.

### Legacy layout

The backing `Vec<i32>` stores:

```text
[head, tail, free_head, count, capacity,
node_0_prev, node_0_next, node_0_value,
node_1_prev, node_1_next, node_1_value, ...]
```
where `head`, `tail`, `free_head` are node indices or `-1` (nil).

## Module `std::collections::pq`

- Source: [`../../../std/collections/pq.ark`](../../../std/collections/pq.ark)
- Manifest-backed functions: 0
- Stability: n/a

`PriorityQueue<T>` — binary min-heap over a flat `Vec<T>`.

The heap stores its elements in level order: the root is the minimum and
every parent compares less than or equal to its children. `push` sifts the
new element up from the last slot; `pop` moves the last element into the
root and sifts it down. Empty `pop` / `peek` return `Option::None`, so
there is no `0` sentinel and no panic path.

The legacy `std::collections::linear::pq_*` free functions were retired
under ADR-087; this type is the replacement surface and does not expose
their `[count, ...heap]` layout.

**Availability:** All targets (`wasm32` + `wasm32-gc`). No host capability required.

## Module `std::collections::bimap`

- Source: [`../../../std/collections/bimap.ark`](../../../std/collections/bimap.ark)
- Manifest-backed functions: 0
- Stability: n/a

`Bimap` — a bidirectional map between `i32` keys and `i32` values.

A bimap maintains a one-to-one correspondence between keys and values.
Each key maps to exactly one value, and each value maps to exactly one key.
Inserting a `(key, value)` pair automatically removes any existing pair with
the same key or the same value.

The backing store is a flat `Vec<i32>` of `[key, value, ...]` pairs. Lookup,
insertion, and removal scan that vector, so they are O(n) in the number of
pairs. Keeping the representation flat is required because the runtime Vec
storage has no nested generic pair container.

Construct with `Bimap::new()` and use the receiver methods; the former
`bimap_i32_i32_*` free functions were retired by #917 with E0100
replacement hints.

**Availability:** All targets (`wasm32` + `wasm32-gc`). No host capability required.

## Module `std::collections::trie`

- Source: [`../../../std/collections/trie.ark`](../../../std/collections/trie.ark)
- Manifest-backed functions: 0
- Stability: n/a

`Trie` — a prefix tree with `String` keys and `i32` values.

A trie (prefix tree) stores key-value pairs where keys are strings, enabling
prefix-based lookups: "does any key start with `P`?", "find all values
with prefix `P`". Common uses include autocomplete, routing tables, and
symbol interning.

Implemented as a Vec-backed node pool. Each node has:
- 256 child slots (one per byte value), each an index into the node pool
or `-1` (no child)
- a `has_value` flag (0 or 1)
- an associated `i32` value

Construct with `Trie::new()` and use the receiver methods; the former
`trie_*` free functions were retired by #917 with E0100 replacement hints.

**Availability:** All targets (`wasm32` + `wasm32-gc`). No host capability required.

### Node pool layout

The backing `Vec<i32>` stores:
```text
[root_index, node_count, free_head,
node_0: child_0..child_255, has_value, value,
node_1: child_0..child_255, has_value, value, ...]
```
Each node occupies `256 + 2` slots.
